## 解くべき問題

### 検査の単位を決める (00 の 4.3)

**これを最初に決める。** 決まらないと呼び出し回数も上限も見積もれない。

実測 (cmdmuse の Go 19ファイル): 日本語コメント行 327、うち行末コメント 24、
**日本語を含むコメント段落 184。**

| 単位 | 段1 の観点5本での呼び出し |
|---|---|
| 段落 | **920 回** |
| 1ファイル分の段落をまとめる | 95 回 |

前の版は「ファイル数 × 観点数」で数えて桁を外した。

**まとめる案は要件に抵触しない。** `L3-01` が禁じているのは
「1プロンプトに複数観点を並べない」であって、複数段落ではない。
まとめれば `L3-07` のプロンプトキャッシュも効く (本文がファイル単位で固定される)。
そのとき段落の行番号を元ファイル基準で本文に埋める必要がある。

### 言語ごとのマーカー

**全マーカーを全ファイルに当ててはならない。** 実測した誤爆:

```
internal/llm/prompt.go:35   "probe": "git rev-parse --git-dir"     ← -- で誤爆
tuning/export_snapshot.py   ap.add_argument("--name", help="…")     ← argparse 全行
internal/llm/prompt.go      b.WriteString("## 実行環境\n")           ← # で誤爆、10行以上
```

`--` は SQL / Lua / Haskell の記法で Go・JS・Python には無い。
`#` を Go / JS に当てると文字列リテラル中の Markdown 見出しを拾う。

**この道具自身のリポジトリを走査すると誤爆する。**
拡張子 → マーカー集合の対応表が要る。

### 段落の切り出し

**区切りに「コメントでない行」を入れる。** 前の版は「空行」と「空コメント」しか
挙げず、間にコードを挟んだ2つのコメント塊が1段落になった。規則どおり実装して
実測したところ **26段落が融合**した。

```
internal/probe/probe.go
  192: builtinProbe は command -v / which / type / test を自前で処理する。
  196: command -v X / type X          ← 間の 193-195 は関数本体
```

段落を「**連続する**コメント行の塊」と定義し、行番号が不連続になった時点で切る。

適用順も決める。空コメント (`//` だけの行) は意味の区切りとして使われるので、
日本語フィルタより先に切らないと別々の説明が融合する。

### 行末コメントを連結しない

連結すると**元ファイルのどこにも存在しない文字列**ができる。

```go
End   int    // 閉じ括弧の次の位置 (バイト)
Text  string // 括弧の中身
```
→ 「閉じ括弧の次の位置 (バイト)括弧の中身」

cmdmuse で 24 行 (約7%) が行末コメント。1行1段落とする。

### 引用の検証先 (要件 `L3-05`)

`L3-05`「引用が原文に存在しない finding は機械的に破棄する」の**「原文」を
元ファイルと定義する。** 抽出結果ではない。

`llm.js` の `verifyEvidence(text, evidence)` は渡された `text` (= 段落) と
照合している。定義を変えるなら第1引数を `documents.body` にする実装変更が要る。
段落に行番号を埋めて渡す場合は、埋めた行番号を除いてから照合する。

**そのままにすると、GitHub の issue にファイル内に存在しない引用が載る。**

### 行番号の写像

`findings.line` には常に元ファイル基準の行番号を入れる。

- `llm.js` の `withLineNumbers` は渡したテキストに 1..N を振る
- `lint.js` は `m.loc?.start?.line` をそのまま入れる。**L1 も写像が要る**

`document_spans` の `start_line` を基準に補正する。

### textlint をコメントに当てるか

`lint.js` は仮想パスを `document.md` に固定している。コメント段落を渡すと
Markdown として構文解析され、`// 1. 手順` は番号付きリスト、`// # 見出し` は
見出しとして扱われ、`sentence-length` や `max-ten` の当たり方が変わる。

コメント用の仮想パスを使うか、当てないかを決める。

**既存の不具合**: `lint.js` の `getLinter` は `linterPromise` を
`configPath` に関わらず1度しか生成しないため、要件 `L1-06` の
プロファイル切り替えは現状効かない。段落ごとに設定を変える案があるならここも直す。

### `documents.body` に何を入れるか

- 抽出したコメントだけ → K-03 (コードと食い違っていないか) に渡すコードが無い。
  画面でもコードが見えず、コードに対する注釈を登録できない
- ソースファイル全文 → `lint.js` が `.go` を Markdown として解釈する

**全文を入れ、抽出結果は `document_spans` に持つ**のが素直だが、決めること。

### 抽出の誤りは却下では吸収できない

抽出の誤りは指摘の妥当性の誤りではない。文字列リテラルを誤って拾った結果を
利用者が却下すると、その却下は「この指摘は採用されない」という教師データになり、
判定器は**入力側のバグを覚える**。

抽出バグは系統的なので (argparse 行や `##` 文字列は毎回同じように誤爆する)、
「却下で吸収できる」という緩和策は成り立たない。抽出側で直す。

`prepare_data.py` がコードブロック・見出し・表を除外しているのと同じ理由で、
UI 文字列やプロンプト断片を負例に混ぜてはならない。

### `findings` から段落を辿れるようにする

`findings.span_id` が無いと、ある指摘がどの段落から出たのかを後から辿れない。
抽出の誤りを見つけたときに原因の span を特定できない。

### 対応する拡張子

Go / JS / TS / Python から始める。それ以外をどうするかは未決。
