### 1.1 この文書で決めないもの

- 走査・キャッシュ・上限の仕組み。02 が決めている (実装はまだ無い)。
  **本書は 02 の決定に接続先という材料を足すだけで、02 の本文は書き換えない**
- 観点を増やすかどうか (04)、検査の単位 (03)
- コスト上限の実数。要件 `OPEN-08` は未決のまま。本書が用意するのは

- 要件 `L3-02` の「初版は `D-01` の1本」。接続先を増やしても観点は増やさない

### 1.2 02 との順序

**本書は 02 より先に入れる。** 理由は3つ。

1. **求められているのは OpenRouter を使えるようにすることである。** 02 は
   実装がまだ無く、規模が大きい (走査の表、非同期化、キャッシュ、上限)。
   02 を待つと、接続先を選べるようにする話がそのぶん止まる
2. **02 が入るまでキャッシュは存在しない。** 本書が接続先を2つにしても、
   「別の接続先の結果が当たる」ことは起きない。起きるのは
   「接続先を鍵に持たないまま 02 のキャッシュを入れたとき」だけで、
   それは 02 の実装が本書の 11章を守れば防げる
3. 本書の移行は `review_aspects` への列の追加だけで、02 が作る表
   (`scans` ほか) に依存しない。先に入れても、02 の移行はそのまま後ろに積める

**02 を先にする理由として一度は挙げたが、成り立たなかったものを残す。**

| 挙げた理由 | 成り立たない理由 |
|---|---|
| `llm.js` の `chat()` を2回変えることになる | 変える行は同じでも、変更の中身は別 (02 は返り値に `model`、本書は引数に接続先と返り値に `usage`)。どちらが先でも2回変わる。差分の読みやすさは、順序を決める理由としては軽い |
| 移行の番号が衝突する | 番号は適用した順に振るだけなので、どちらが先でも衝突しない (10.4) |
| 02 のキャッシュが接続先を知らないまま入る | キャッシュは 02 と同時に入る。本書が先なら、キャッシュが存在し始める時点で `endpoint` の列は既にある |

**02 を実装するときに守る条件は 11章にまとめた。** 02 の本文にも、
6.1 の問い合わせと 5.2 の走査の鍵の箇所に、参照を1行ずつ足してある。

## 2. 用語と品質目標

00 の 5章の語をそのまま使う。本書で足す語は2つだけ。

| 語 | 意味 |
|---|---|
| 接続先 | 1回の LLM 呼び出しを送る先。URL・モデル・キーの置き場所・外部かどうかを1組にしたもの。設定と API と記録では英語の名前 `endpoint` を使う |
| `EP-*` | **本書 (05) の未決事項の接頭辞** (19章) |

**品質目標に順位を付ける。** 下の順で、上が下に勝つ。

1. **利用者が選んでいない接続先へ本文を出さない**
2. **本文を出した先が記録に残り、あとから引ける**
3. 測定の記録が正しい (実際に答えたモデル、費用、`finish_reason`)
4. 使いやすさ (再起動なしで切り替わる、設定が短い)

順位が効く場面を1つ挙げる。手元の接続先が落ちているときに外部へ回せば 4 は上がるが、
1 に反する。**回さない** (6.2)。

## 3. 接続先

### 3.1 状況

いま接続先に相当するものは、環境変数3つ (`JUSTIC_BASE_URL` /
`JUSTIC_MODEL` / `JUSTIC_API_KEY`) とコード中の定数に散っている。
定数は `temperature: 0` と `max_tokens: 2000` の2つである。
OpenRouter を1つの接続先として足すには、
少なくとも次が接続先ごとに違う。

- モデル ID (手元のルーターは空でよい。OpenRouter は必須)
- キー (手元は端末別の集計用、OpenRouter は認証)
- 思考の抑え方 (手元は `chat_template_kwargs`、OpenRouter は `reasoning`)
- `max_tokens` と `temperature`
- 外部かどうか

### 3.2 決定 — 接続先は1つの JSON のオブジェクトで表す

1つの接続先が持つ項目を次のとおり決める。

| 項目 | 型 | 必須 | 意味 |
|---|---|---|---|
| `name` | 文字列 | ○ | 接続先の名前。`[a-z0-9_-]` の 1〜32 文字。API の要求・記録・画面はこれで指す |
| `title` | 文字列 | | 画面に出す名前。無ければ `name` を出す |
| `base_url` | 文字列 | ○ | `/chat/completions` を足す前までの URL |
| `model` | 文字列 | | モデル ID。空文字は「送らない」(接続先の既定に任せる) |
| `external` | 真偽 | ○ | **本文が手元の外へ出るか。** 推測しない (7.3) |
| `key_file` | 文字列 | | API キーの置き場所 (5章)。無ければキーを送らない |
| `max_tokens` | 整数 | ○ | 1回の応答の上限 (8.4) |
| `temperature` | 数値または `null` | ○ | `null` は「送らない」(9章) |
| `timeout_ms` | 整数 | ○ | 1回の呼び出しのタイムアウト |
| `thinking` | オブジェクト | ○ | 思考の抑え方 (8.3) |
| `response_format` | 真偽 | | `true` のとき `{"type":"json_object"}` を送る。既定 `false` (8.6) |
| `provider` | オブジェクト | | OpenRouter の `provider` の指定をそのまま入れる (7.5)。他の接続先では書かない |
| `headers` | オブジェクト | | 追加のヘッダ。`Authorization` は書けない (5.5) |

`external` を**設定に書かせて URL から推測しない**理由は 7.3 に書く。

### 3.3 検討した代替案とそれを採らない理由

| 案 | 採らない理由 |
|---|---|
| 接続先ごとに環境変数を増やす (`JUSTIC_OPENROUTER_URL` など) | 接続先が2つで変数が 12 個を超える。`provider` のような入れ子を環境変数に押し込むと、文字列を JSON として読み直すことになる。増やすたびに `.env.example` と `run.sh` の両方を直す |
| 接続先の種類を justic のコードに書く (「OpenRouter なら `reasoning` を送る」) | 接続先を足すたびにコードが増える。要件 `L3-08` はモデル ID を設定に出すことを求めており、接続先も同じ理由で設定に出る |
| YAML にする | `js-yaml` が依存に増える。`web/package.json` の依存は5件で、JSON は node がそのまま読める |
| 1つの接続先に複数のモデルを持たせる | 観点ごとにモデルを変える話 (要件 §7 の `D-08` に Opus 5) は 04 が決める。いま持たせると、記録の側で「どのモデルで走ったか」が接続先の名前から引けなくなる |

### 3.4 代償

設定ファイルが1つ増える。接続先を足すには JSON を手で書く必要があり、
書き間違い (とくに `external`) が起きうる。手当ては 7.3 と R-22。

## 4. 設定の置き場所

### 4.1 決定 — `~/.config/justic/endpoints.json`

**正は `~/.config/justic/endpoints.json`。リポジトリには
`endpoints.example.json` を置く (キーは書かない)**。
環境変数 `JUSTIC_ENDPOINTS` でパスを変えられる。これは試験 (16章) のために要る。

```json
{
  "default": "local",
  "endpoints": [
    {
      "name": "local", "title": "手元のルーター",
      "base_url": "http://127.0.0.1:18080/v1",
      "model": "", "external": false,
      "key_file": "~/.config/justic/local-key",
      "max_tokens": 4000, "temperature": 0, "timeout_ms": 120000,
      "thinking": {"mode": "chat_template_kwargs"}
    },
    {
      "name": "openrouter", "title": "OpenRouter",
      "base_url": "https://openrouter.ai/api/v1",
      "model": "google/gemini-3.8-flash", "external": true,
      "key_file": "~/.config/justic/openrouter-key",
      "max_tokens": 8000, "temperature": null, "timeout_ms": 180000,
      "thinking": {"mode": "reasoning", "effort": "low", "exclude": true},
      "provider": {"data_collection": "deny", "zdr": true}
    }
  ]
}
```

### 4.2 検討した代替案とそれを採らない理由

| 案 | 採らない理由 |
|---|---|
| リポジトリの中 (`web/endpoints.json`) | 手元の設定が git の差分に出る。`.gitignore` で外すと、例と実物が同じ名前で並び、どちらを編集したか分からなくなる。チェックアウトを増やすたびに書き直す |
| `.env` に JSON の文字列として入れる | 1行に押し込むので読めない。編集のたびに再起動が要る (`node --env-file` は起動時に1回読む) |
| DB の表に持つ | 設定を変えるのに DB が要る。`db/pg.sh` が止まっているときに接続先を直せない。キーと同じ表に入れたくなる誘惑も生む (5.3) |
| `~/.config/llm/` に相乗りする | あそこはルーターの設定で、持ち主が違う。justic が書き換えるとルーターが壊れる |

### 4.3 いまの環境変数との関係

**`JUSTIC_BASE_URL` / `JUSTIC_MODEL` / `JUSTIC_API_KEY` は残す。**
設定ファイルが無いときだけ、この3つから接続先を1つ組み立てる。

```
name        "local"
base_url    JUSTIC_BASE_URL ?? "http://127.0.0.1:18080/v1"
model       JUSTIC_MODEL
external    false
キー        JUSTIC_API_KEY の値をそのまま使う (キーファイルは読まない)
その他      max_tokens 4000 / temperature 0 / timeout_ms JUSTIC_L3_TIMEOUT_MS
            thinking は {"mode":"chat_template_kwargs"}
```

つまり**設定ファイルを置かなければ、いまと同じ1接続先で動く**
(`max_tokens` だけは 2000 から 4000 に変わる。8.4)。

**設定ファイルがあるときは環境変数を読まない。** 両方を混ぜると、
どちらが効いているかが設定を見ても分からない。ただし黙って無視すると、
設定ファイルを置いた瞬間に `JUSTIC_API_KEY` が効かなくなって 401 になり、
理由が分からない。**設定ファイルがあるのに3つのどれかが設定されていたら、
起動時に「効いていない」と1行出す。**

### 4.4 設定が無いとき、接続先が0件のとき

| 状態 | 振る舞い |
|---|---|
| 設定ファイルが無い | 4.3 の `local` 1件。いまと同じ |
| 設定ファイルが読めない (JSON が壊れている) | **起動を止める。** 接続先が分からないまま走らせると、どこへ送るか決まらない |
| `endpoints` が空 | L3 を無効として扱う (`JUSTIC_L3=0` と同じ)。`/api/health` の `endpoints` が空配列になるので画面から気づける |
| `default` が無く、外部でない接続先がちょうど1つ | それを既定にする |
| `default` が無く、外部でない接続先が0個または2個以上 | 既定を決めない。要求に `endpoint` が無ければ 400 (6.1) |

**`default` に外部の接続先を書くこともできる。** 止めない。
利用者が明示的に書いたものだからで、画面には常に外部の印が出る (13章)。

### 4.5 読み直し

**接続先の一覧は起動時に1回読む。キーファイルは呼び出しのたびに読む** (5.2)。

理由: 接続先を足す操作は稀だが、キーの差し替え (失効・再発行) は外部の接続先で
現に起きる。OpenRouter のキーは作成時の応答でしか平文が返らないので、
失くしたら作り直しになる (OpenRouter の確認メモの 6)。
一覧まで呼び出しのたびに読み直すと、**1回の走査の途中で送り先が変わりうる**。
02 の 3.3 が「途中まで別のモデルで走った走査が1つの `scan_id` にまとまる」ことを
理由に再開を禁じたのと同じ壊れ方をする。

**代償。** 接続先を足したら justic の再起動が要る (`EP-06`)。

## 5. API キーの保存場所

### 5.1 守る条件

1. リポジトリに入らない
2. DB に入らない
3. ログ・API の応答・画面に出ない
4. コマンドライン引数に出ない

### 5.2 決定 — 接続先ごとの 0600 の1行ファイル

**キーは接続先ごとの1行ファイルに置き、`endpoints.json` の `key_file` に
パスを書く**。**呼び出しのたびに1行目を読む**。**既定の置き場所は
`~/.config/justic/<name>-key`**。

これは手元にすでにある形と同じである。`~/.config/llm/claude-key` は
`-rw------- 1 oosaw oosaw 40` の1行ファイルである。`~/llm-tx` は
`--key-file` に渡されたファイルの1行目を読む (`llm-tx` 291〜296行)。
`llm-tx` の使い方には「コマンドライン引数で直接キーを渡す形は無い
(シェル履歴に残るため)」と書いてある。同じ理由が justic にも当てはまる。

理由を4つ書く。

1. **再起動なしで差し替えられる。** 呼び出しのたびに読むので、キーを入れ替えて
   次の走査から効く。外部の接続先ではキーの失効が起きる
2. **プロセスの環境に載らない。** 環境変数に置くと子プロセスへ継承され、
   `/proc/<pid>/environ` からも読める
3. **接続先と1対1で並ぶ。** どのキーがどこへ行くかが設定の1行で分かる
4. **手元に同じ形がある。** 置き場所の作法 (0600、1行、先頭行を読む) を
   新しく決めずに済む

### 5.3 検討した代替案とそれを採らない理由

| 案 | 採らない理由 |
|---|---|
| `.env` に接続先ごとの変数を足す (いまの方式の延長) | 差し替えに再起動が要る (`node --env-file` は起動時に1回読む)。プロセスの環境に載り、子へ継承される。設定 (接続先) とキー (変数名) が2箇所に分かれ、増やすたびに両方を直す |
| 設定に環境変数の**名前**だけ書く (`"key_env": "OPENROUTER_API_KEY"`) | 値の置き場所は `.env` のままなので、上の欠点をそのまま引き継ぐ。設定の段が1つ増えるだけで、守る条件は1つも増えて満たされない |
| `endpoints.json` に直接書く | 設定は URL とモデルを見るために開く。開くたびにキーが目に入る。設定を貼って相談する経路 (issue、レビュー、この設計書) で漏れる |
| DB の表に持つ | 5.1 の 2 に反する。`db/backups/` と `pg_dump` の出力にキーが乗る |
| OS のキーチェーン (libsecret / gnome-keyring) | **WSL の無人環境だから採らない。** キーチェーンは画面のロック解除に相当する操作で開く前提の仕組みで、ここには解除を打つ人も常駐する D-Bus セッションも無い。`run.sh` に起動手順が増え、開けないときはレビューが1回も走らずに落ちる。得るもの (メモリ上の暗号化) に対して、失われる可用性が大きい |

### 5.4 権限の検査 — 読むたびに見て、拒む

**キーファイルを読む直前に権限を見る。group か other に読み権限があれば
(`mode & 0o077` が 0 でなければ) キーを読まずに失敗させる。**
警告ではなく拒否にする。

理由: 警告はログの1行として流れる。キーは漏れても動き続けるので、
**静かに使い続けられるほうが悪い。** 拒めば最初の1回で気づく。

起動時ではなく読むたびに見るのは、5.2 で呼び出しのたびに読むと決めたためで、
差し替えたファイルの権限が緩んでいたら次の呼び出しで止まる。

**代償。** `umask` の違うところでキーを作ると、レビューが1回も走らずに落ちる。
エラーの文言に直し方 (`chmod 600 <パス>`) を書く。
ファイルの無いとき・1行目が空のときも同じく拒む。ただし `key_file` が
設定に書かれていない接続先は「キーを送らない」であって、失敗ではない。

### 5.5 キーが出ない場所

| 場所 | どうするか |
|---|---|
| `review_aspects` | 接続先の**名前**だけを書く。キーもパスも書かない (10章) |
| `/api/health` | `hasKey` の真偽値だけ返す。パスも長さも返さない (12章) |
| `chat()` のエラー文言 | いまと同じく `res.status` と応答本文の先頭 200 文字だけ。**要求のヘッダは出さない** |
| `endpoints.headers` | `authorization` という名前のヘッダは設定から書けない。書いてあったら起動時に落とす。設定にキーを書く抜け道を1つ潰す |
| 画面 | 接続先の名前と外部の印だけ (13章) |
| `.gitignore` | `endpoints.json` と `*-key` を足す。設定を `~/.config` に置く決定の保険で、リポジトリの中に置いた人を助ける |

### 5.6 手元のルーター向けのキー

02 の 8.3 は「justic 用に発行したキーの記録を `~/llm-tx` で見れば、走査1回あたりの
再利用トークン数が分かる」と書いており、justic 専用のキーが発行されている前提に立つ。
**本書の仕組みがそのまま使える。** ルーターの画面で justic 用のキーを発行し、
`~/.config/justic/local-key` に 0600 で置く。置いたパスは `endpoints.json` の
`local` の `key_file` に書く。記録は `~/llm-tx --key-file ~/.config/justic/local-key` で読む。

**ルーターのキーは認証ではない。** `~/llm-router.py` の 146行に
「用途は **端末ごとの記録** であって認証ではない。キーが無くても通す」とある。
ルーターがやっているのは3つだけである。`extract_key` (197〜206行) が
`Authorization: Bearer` から文字列を取る。`identify` (208〜218行) が
それをキー表の名前に引き当てる。`touch_key` (187〜196行) が使用回数を足す。
**キーが未登録でも拒まれない。**
したがって手元の接続先では、キーが無くても動く。無いと記録が端末別に分かれないだけである。

## 6. 接続先の選び方

### 6.1 決定 — 要求ごとに名前で選ぶ。無い名前は 400

- レビューの要求の本文に `endpoint` (接続先の名前) を足す。**いまある3経路
  (`POST /api/reviews`、`/api/reviews/github/pr`、`/api/reviews/github/branch`)
  すべてが受け取る**。 02 を実装したら `POST /api/scans` が引き継ぐ (17章)
- 省略時は 4.4 の既定を使う。既定が決まっていなければ **400**
- 設定に無い名前は **400**。文言に選べる名前を並べる

**無い名前を既定に落とさない。** 落とすと、外部を指定したつもりの要求が手元へ流れ、
逆に手元を指定したつもりの要求が既定の外部へ流れる。どちらも黙って起きてはいけない。

**1回の要求の中で接続先は変わらない。** 要求で1つ選び、その要求で走る
全レビュー・全観点がそこへ行く。観点ごとに接続先を変える話 (要件 §7 のモデル割当) は 04 と
一緒に決める (`EP-05`)。記録は観点ごとに持つので (10章)、表の作りは足りている。

### 6.2 決定 — 接続先どうしの黙った切り替えを禁じる

**手元の接続先が落ちていても外部へ回さない。外部が 429 や 402 を返しても
手元へ落とさない。どちらの向きも禁じる。**

理由を3つ書く。

1. **利用者が選んでいない先に本文が出る。** 手元を選ぶのは「外に出さない」という
   判断であって、可用性の設定ではない。品質目標の 1 に真正面から反する
2. **記録の系統が混ざる。** 1つの走査の中で `review_aspects.model_id` と
   `endpoint` が入れ替わる。01 の 7.3 は recall を
   `(model_id, prompt_version)` が指定と一致する集合で測るので、
   混ざった走査は分母の一部だけが別系統になる。02 の 3.3 が走査の再開を禁じた
   理由と同じ
3. **費用が黙って発生する。** 手元は電気代、OpenRouter は残高。切り替えが黙って
   起きると、押した操作と使った金が結び付かない

代わりにどうするか。繋がらなければ `status='error'` にし、同じ理由が2回続いたら
そこで止める (14章)。**利用者が接続先を選び直してやり直す。**
02 が入るまでは、やり直すと最初のファイルから走り直す。済んだファイルが
0回になるのは、02 のキャッシュが入ってからである (02 の 6章)。

### 6.3 検討した代替案とそれを採らない理由

| 案 | 採らない理由 |
|---|---|
| 接続先を設定の並び順で試す (落ちたら次) | 6.2 の3つがそのまま起きる。並び順という、設定を見ても目立たないものが送り先を決める |
| 外部を「明示的に許可したときだけ切り替える」 | 許可は走査の前に1回押すもので、切り替わるのは数分後。押した時点と出る時点が離れるほど、何に同意したか分からなくなる |
| 接続先を走査ではなく `.env` で選ぶ (いまの方式のまま) | 切り替えに再起動が要る。再起動をまたぐので、記録から見て「いつ何が変わったか」が追えない |
| 接続先を観点ごとに選べるようにする | いま観点は `D-01` の1本 (要件 `L3-02`)。使う場面が無い機構を先に作らない。`EP-05` |

### 6.4 代償

外部の接続先を使うには、毎回それを選ぶ。手元が落ちているときは、
利用者が気づいて選び直すまで検査が進まない。**止まったことは画面に出る**。
02 が入るまでは応答の `stopped` と `notScanned` (14.3) を既存の注記の場所
(`app.js` 506行) に出し、02 が入れば走査の進捗と 9.3 の出し分けが引き継ぐ。

### 7.1 外部の接続先に送るもの

| 3 | 要求の項目 | `model` / `max_tokens` / (設定に応じて) `temperature` / `reasoning` または `chat_template_kwargs` / `response_format` / `provider` |
| 4 | ヘッダ | `content-type` と `Authorization: Bearer <キー>`、`headers` に書いたもの |

行番号を付けるだけなので、受け取った側は原文をそのまま復元できる。

### 7.2 送らないもの

| 送らないもの | 根拠 |

| 文書の題 | `reviewAspect(text, aspect)` は本文と観点しか受け取らない。題は `owner/repo:branch path` の形 (`server.js` 249行、280行) で、リポジトリ名とパスを含む |

| `HTTP-Referer` / `X-OpenRouter-Title` | 7.6 |

### 7.3 決定 — 外部かどうかは記録に値として残す

**`external` は設定に書かせ、URL から推測しない。記録 (`review_aspects`) にも
そのときの値を書き写す。**

推測しない理由: `127.0.0.1` でない接続先がすべて外部とは限らず (社内の別の機械)、
`localhost` に見えて外へ転送される構成も作れる。**推測が外れたときに起きるのは
「外部なのに手元として記録される」で、これは黙って起きて、あとから区別できない。**

記録に書き写す理由: 設定ファイルは後から書き換わる。`external` を参照で引くと、
**設定を1行直した瞬間に過去の記録の意味が変わる。**
02 の 6.3 が `model_id` を実測値にしたのと同じ理由で、記録は値を持つ。

**書き間違いへの手当て。** `base_url` のホストが `127.0.0.1` / `localhost` /
`::1` のどれでもないのに `external: false` と書いてあったら、起動時に警告を出す。
止めはしない (社内の別の機械という正しい書き方があるため)。逆向き
(ループバックなのに `external: true`) は安全側なので何も言わない。

### 7.4 どの文書が外に出たかを引く

```sql
-- 外部の接続先に本文を送ったもの。新しい順
select d.id   as document_id, d.sha256, d.title,
       ra.endpoint, ra.model_id, ra.aspect_id,
       ra.started_at, r.id as review_id, r.source_kind, r.source_ref
  from review_aspects ra
  join reviews   r on r.id = ra.review_id
  join documents d on d.id = r.document_id
 where ra.endpoint_external
 order by ra.started_at desc;
```

**`endpoint` は「本文を送った先」という意味にする**。 送っていない行
(キャッシュの写し = 02 の 6.2、`status='skipped'`) は `endpoint` と
`endpoint_external` のどちらも NULL。だから上の問い合わせは `from_cache` を見る必要がない。

索引は `review_aspects (started_at desc) where endpoint_external` の部分索引を張る
(10.3)。外部へ出した行は全体の一部なので、部分索引で足りる。

### 7.5 OpenRouter 側のデータ保持

OpenRouter の確認メモ (2026-09-11 確認) に書いてあることだけを使う。

| 層 | 既定 | justic の要求で指定できるか |
|---|---|---|
| OpenRouter 自身の保存 | **既定では保存しない。** 保存は opt-in (Observability の Private Input & Output Logging、Privacy の OpenRouter Use of Inputs/Outputs) | **できない。** アカウントの設定なので、justic の外で確かめる |
| メタデータ (トークン数、遅延など) | 常に保存される。本文は含まない | できない |
| 提供元の保存・学習 | 提供元ごとに違う。既定 (`data_collection: "allow"`) は学習しうる提供元も使う | **できる。** `provider.data_collection: "deny"` |
| 提供元の保存 (ZDR) | 提供元ごとに違う | **できる。** `provider.zdr: true`。アカウント設定との OR なので、有効化はできるが無効化はできない |

**決定。justic のコードから `provider` を注入しない**。**`endpoints.example.json` の
OpenRouter の例に `{"data_collection": "deny", "zdr": true}` を書いておく**。

理由: 注入すると、設定に書いていないものが送られる。しかもこの2つは
ルーティングを絞るので、条件を満たす提供元が無ければ要求が落ちる。
OpenRouter の確認メモの 5-3 は、Google 群で ZDR を有効にすると
AI Studio のエンドポイントが外れ、Vertex だけが残ると書いている。
**黙って注入した設定で落ちると、理由が justic の側から見えない。**
例に書いておけば、外したのは利用者の判断になる。

**代償。** 例をコピーせずに設定を書いた場合、`data_collection` は既定の `allow` に
なる。手当てとして、`/api/health` は `provider` の中身をそのまま返し (秘密ではない)、
画面の接続先の選択に添える (13章)。

### 7.6 決定 — 名乗るヘッダを既定では送らない

`HTTP-Referer` と `X-OpenRouter-Title` は任意のヘッダである。
**両方を送ると openrouter.ai 上にアプリのページが作られ、ランキングに出る**
(OpenRouter の確認メモの 1)。`HTTP-Referer` が無ければページは作られない。

**決定。既定では送らない。** 送りたければ `endpoints.headers` に書く。
理由: 送って得られるもの (向こうの画面での識別) を justic は必要としない。
外に出る情報は、本文だけで十分に多い。

### 8.3 決定 — 思考の抑え方を接続先の項目にする

`thinking` は3つの形のどれかを取る。

| `mode` | 送るもの | 想定する接続先 |
|---|---|---|

**`effort` の値は設定に書く。justic は既定値を持たない。**
根拠は OpenRouter の確認メモの 4-1 である。`google/gemini-3.8-flash` は
`reasoning.mandatory: true` で `default_enabled: true` である。
`supported_efforts` は `high` / `medium` / `low` の3つだけである。

- **思考は止められない。** `effort: "none"` は送ってはいけない (モデルが拒否する)

**接尾辞付きのモデル名 (`…-think`) を `model` に書かない。** 8.2 の 3 のとおり
ルーターが `chat_template_kwargs` を上書きし、justic の指定が消える。
上書きされたことは応答からは見えない (`model` は接尾辞付きの名前で返る) ので、
設定で避けるしかない (`EP-08`)。

### 8.4 決定 — `max_tokens` を接続先の項目にする

02 の 7.3 と同じ形で暫定値を置く。

| 接続先 | 暫定値 | 根拠 | 差し替える場所 |
|---|---|---|---|
| 手元のルーター | 4000 | いまの 2000 は思考ぶんで使い切った (1章)。倍にするが、測った値ではない | `endpoints.json` の `max_tokens` |
| OpenRouter (`google/gemini-3.8-flash`) | 8000 | 思考を止められず、消費するトークン数は Google 側が決める。公開された境界値は無い (OpenRouter の確認メモの 2-5) | 同上 |

**要求の項目名は `max_tokens` のままにする。** OpenRouter の OpenAPI では
`max_tokens` は deprecated である。案内されているのは `max_completion_tokens`
(OpenRouter の確認メモの 2-3)。手元の llama-server が `max_completion_tokens` を
読むかは **未確認**である。両方に通る名前は `max_tokens` のほうで、
deprecated は「効かない」ではない。接続先ごとに名前を変える機構は、
確かめる手段ができるまで作らない (`EP-01`)。

`top_provider.max_completion_tokens` は 65536 (OpenRouter の確認メモの 4-1) なので、
8000 は上限に当たらない。

### 8.5 決定 — `finish_reason` を記録し、「途中で切れた」を別の文言にする

**`review_aspects.finish_reason` に応答の `choices[0].finish_reason` をそのまま書く**。
**`length` のときは、`error` の文言を「出力が `max_tokens` (N) に達して途中で切れた」
にする**。

いまは `parseFindings` が「JSON が見つからない」を返す (`llm.js` 108行)。
切れたのか、モデルが JSON を返さなかったのかが読めない。手当ては2箇所に要る。

- `reviewAspect` が `finishReason` を見て文言を変える
- 画面は `finish_reason` を見て「途中で切れた」と出す (13章)

**`review_aspects.status` の CHECK は増やさない。** `'truncated'` のような値を
足したくなるが、採らない。理由は2つ。

1. 01 の 6.1 と 02 の 10.1 が「この CHECK は変更しない」と決めている。
   貼り直すと 02 が 14章で避けた作業がここで発生する
2. 集計から見れば、「JSON が読めなかった」も「途中で切れた」も
   **指摘として使えない**点で同じで、分けたいのは原因のほうである。
   原因は `finish_reason` の列で数えられる

**代償。** `status` だけを見ると両方が `parse_error` に見える。画面と

### 8.6 決定 — `response_format` は既定で送らない

要件 `L3-03` は「出力は JSON 固定」を求めており、`{"type":"json_object"}` を
送れば形が揃いやすくなる。`google/gemini-3.8-flash` の `supported_parameters` には
`response_format` がある (OpenRouter の確認メモの 4-1)。

**それでも既定では送らない。** 理由は2つ。

1. 手元の llama-server が `response_format` を読むかは **未確認**。
   要求を送らずには確かめられない
2. OpenRouter では、対応しないエンドポイントへルーティングされると
   `response_format` は無視される。確実にするには
   `provider.require_parameters: true` を併せて送ることになり、
   ルーティングがさらに絞られる (OpenRouter の確認メモの 2-4)。**指摘の形を揃えるために、
   どの提供元が答えるかを変える**のは代償が大きい

設定の `response_format: true` で送れるようにはしておく。効くかどうかは
測ってから決める (`EP-03`)。いずれにせよ `parseFindings` の検証は外さない。

## 9. `temperature`

いまは `temperature: 0` を固定で送っている (`llm.js` 78行)。

**決定。`temperature` を接続先の項目にし、`null` を「送らない」と定義する。
手元は `0` のまま、OpenRouter の例は `null` にする。**

理由。「Gemini 3 系では `temperature` を 1.0 にすべき」という趣旨の記述は、
**OpenRouter のドキュメントには無い (未確認)**。
これは OpenRouter の確認メモの 10 による。
`google/gemini-3.8-flash` の `default_parameters` も空である。
確実に言えるのは1つだけで、**送らなければ OpenRouter は上流に転送せず、
提供元の既定が効く** (OpenRouter の確認メモの 2 の共通の前提)。

| 案 | 採らない理由 |
|---|---|
| すべての接続先で `0` を送り続ける | Google 側の既定を、根拠を確かめないまま上書きすることになる |
| OpenRouter には `1.0` を送る | 「Google の推奨が 1.0」を一次情報で確かめていない。確かめていない値を固定で送ると、結果の再現性の根拠が無くなる |
| 接続先によらず送らない | 手元の接続先では `0` が現に効いており、指摘の揺れを抑えている。変える理由が無い |

**代償。** 接続先によって揺れ方が違う。測定 (01) では
接続先をまたいだ比較をしない。記録に接続先が入るので、分けて数えられる。

`is_byok` も返しうる (OpenRouter の確認メモの 3)。

| 全部を列にする | 接続先ごとに使わない列が並ぶ。向こうの項目が増えるたびに移行が要る |
| `usage` を保存しない | 1回ごとの費用が残らない。15章の材料が作れない |

**代償。** 同じ数字が2箇所に載る。食い違ったときは列を正とし、
`usage_raw` は「そのとき返ってきたもの」として読む。

### 12.1 `GET /api/health` の接続先の一覧

```json
"endpoints": [
```

### 12.2 決定 — health から接続先へ要求を送らない

**外部の接続先にも手元の接続先にも、health から要求を送らない。
設定を読んで返すだけにする。**

理由を3つ書く。

1. **health は画面を開くたびに引かれる。** 外部へ毎回出ると、本文を送っていないのに
   openrouter.ai への接続が画面の表示回数だけ発生する。本書の担保
   (「外部の接続先を選ばない限り外に出ない」16章) がそこで崩れる
2. **確かめても保証にならない。** キーは失効し、残高は減り、提供元は落ちる。
   確かめた瞬間と使う瞬間は違う。「health は通ったのに走査は 402」は普通に起きる
3. **手元の接続先も同じ**。 18080 のルーターは複数の端末が共有していて、
   justic の health のために要求を1件挟むと、その時点のスロットの接頭辞が
   入れ替わる (02 の 8.3 の条件 2)

**代償。** 画面から「いま繋がるか」は分からない。分かるのは
「設定があるか」「キーがあるか」までである。繋がらないことは最初の走査で分かり、
そのときは 14章の文言が出る。

## 14. 失敗したとき

02 の 9章の表に、外部の接続先で起きる失敗を足す。**02 の表は書き換えず、
ここに足す行を書く。** 02 はまだ実装が無いので、当面この表が効くのは
いまの3経路のループのほうである。止め方と応答の形は 14.3 で決める。

| 失敗 | 見分け方 | 決定 | 走査 |
|---|---|---|---|
| キーが無効 (401) | HTTP 401。`error.metadata.error_type = 'authentication'` | `status='error'`。文言は「接続先 <名前> のキーが拒否された」。**キーそのものは出さない** | **1回で止める** (`stopped` / `backend`) |
| 残高切れ (402) | HTTP 402。`payment_required` | `status='error'`。「残高が足りない」 | **1回で止める** |
| レート制限 (429) | HTTP 429。`Retry-After` が付くことがある | `status='error'`。**再試行しない** | **1回で止める** (`stopped` / `rate_limit`) |
| 出力が途中で切れた | `finish_reason='length'` | `status='parse_error'`。文言を 8.5 のものにする | 続ける |
| HTTP 200 なのに本文が `error` | `json.error` があり `choices` が無い | `status='error'`。`error.message` の先頭 200 文字 | 同じ理由で2回続いたら止める |
| モデレーションで弾かれた (403) | `error_type` が `content_policy_violation` / `refusal` | `status='error'`。理由の名前だけ残す | 止める |
| 提供元が見つからない (404 / 503) | `error_type` が `not_found` / `provider_overloaded` など | `status='error'`。`provider` の指定で絞りすぎている可能性を文言に添える (7.5) | 2回続いたら止める |
| キーファイルが読めない・権限が緩い | `chat()` を呼ぶ前に落ちる | `status='error'`。文言に直し方 (`chmod 600`) | **1回で止める** |

**止めた理由の名前は 02 の `stop_reason` に合わせ、値を増やさない。**
02 の 10.2 の `scans` は CHECK を持っている。
`check (stop_reason in ('limit','rate_limit','backend','restart'))` である。
値を足すと、この CHECK を貼り直すことになる (02 の 14章が避けた作業)。
401 / 402 / キーファイルの不備は `backend` にまとめ、**何が起きたかは
`review_aspects.error` の文言で読む。** 429 は `rate_limit` にそのまま当たる。
02 が入るまでは、この名前を応答の `stopped.reason` に入れる (14.3)。
キーファイルの不備は `chat()` を呼ぶ前に落ちるので、そのときは LLM を
1回も呼ばずに止まる。

### 14.1 HTTP のステータスだけで判断しない

OpenRouter の確認メモの 3 のとおり、OpenRouter は**生成が始まったあとの失敗を HTTP 200 で返し、
本文に `error` だけを入れる**ことがある。いまの `chat()` は `res.ok` だけを見て
(82行)、200 なら `json.choices?.[0]?.message?.content ?? ""` を返す (84行)。
**このままだと、失敗が空文字列になって `parse_error` に化ける。**

決定。`chat()` は 200 でも本文に `error` があればそちらを見る。
分岐は `error.metadata.error_type` を使い、無ければ HTTP のステータスを使う。

### 14.2 決定 — justic は再試行しない

**401 / 402 / 429 のどれでも、justic の側で再試行しない。走査を止めて、
利用者がやり直す。**

これは OpenRouter の推奨 (OpenRouter の確認メモの 8:「`Retry-After` を守る指数バックオフで
再試行する」) に従わない選択である。理由を2つ書く。

1. **いまと 02 のどちらも逐次である**。 いまは `reviewOne` をファイルごとに `await` で
   回しており、02 も同時実行1と決めている (02 の 3.2、8.2)。1本の呼び出しが
   数分待つと、その間は全体が止まる。待っていることは画面に出ないので、
   利用者からは固まって見える
2. 401 と 402 は待っても直らない。429 も、外部の接続先では
   「内容が生成されなくても上流のプロンプト処理ぶんを課金されることがある」
   (OpenRouter の確認メモの 8) ので、繰り返すほど費用だけが増える

やり直しの値段は 02 の前後で違う。**02 が入るまでは最初のファイルから走り直す**
(キャッシュが無い)。02 が入れば済んだファイルは0回になる (02 の 6章)。
それでも、待ち続けるより利用者が接続先を選び直せるほうがよい。

**代償。** 一時的な 429 でも止まる。止まった位置は、02 が入るまでは応答の
`notScanned` (14.3)、02 が入れば `scan_items` に残る (02 の 9章)。

### 14.3 02 が入るまで、どう止めて何を返すか

**状況。** `server.js` の3経路は `reviewOne` を同期で呼ぶ。PR 経路は
247〜256行、ブランチ経路は 277〜286行でファイルごとに `for` で回し、
`reviews` の配列を組み立てて最後に1つの JSON を返す (257行、287行)。
`scans` の行も `stopped` という状態も、まだ無い。

**決定。上の表で「止める」と書いた失敗が起きたら、その場でループを抜け、
済んだぶんの `reviews` と、止めた理由を同じ応答に入れて 200 で返す。**

応答に2つ足す。

```ts
stopped: {
  reason: "backend" | "rate_limit";   // 02 の stop_reason と同じ語
  endpoint: string;                   // どの接続先で起きたか
  message: string;                    // 画面に出す文。キーは入れない
} | null;
notScanned: string[];                 // 走らせなかったファイルのパス
```

理由を2つ書く。**済んだレビューを捨てない。** 捨てると、そこまでの L1 の結果と
`findings` が画面から消える。行は DB に入っているので、記録と画面が食い違う。
**500 を返さない。** 一部は成功しているのに、応答の形が「全部失敗」になる。
貼り付け経路 (`POST /api/reviews`) はファイルが1つなので `notScanned` は常に空で、
`stopped` だけが入る。

`reason` を 02 の `stop_reason` と同じ語にしておくと、02 が
`/api/scans` へ寄せるときに画面の文言をそのまま持ち越せる。

**代償。** 3経路の応答の形が2項目ぶん増える。02 が入るとこの2項目は
`scans.status` / `stop_reason` と `scan_items` へ移り、経路ごと消える (17章)。

## 15. 費用

要件 `OPEN-08` (コスト上限) は未決のまま。**本書はこれを決めない。**
決めるための材料を3つ置く。

| 材料 | 置き場所 |
|---|---|
| 1回ごとの費用 | `review_aspects.cost` と `usage_raw` (10章) |
| 1回の検査の合計 | 02 が入るまでは `review_aspects` を `review_id` で束ねて数える。02 が入れば `scan_id` で束ね、`scans.endpoint` で接続先別に出る (11.3) |
| 呼び出し回数の上限 | 02 の 7章が作る。本書は前倒しで作らない |

**justic 側の上限は金額で置かない。呼び出し回数で置く (02 の 7章)。**
理由: 金額で止めるには呼ぶ前に費用が分からなければならない。分かるのは
応答が返ったあと (`usage.cost`) なので、金額で止めると**必ず使ったあとに止まる。**
回数の上限は呼ぶ前に効く (02 の 7.4)。

**ただし、02 が入るまで justic 側に回数の上限は無い。** いまの3経路には
ブランチ走査のファイル数の上限 (`server.js` の `Math.min(maxFiles, 50)`) しか無い。
本書はこれを前倒しで作らない (02 の 7章が走査の表と一緒に作るもので、
片方だけ先に作ると置き場所が二重になる)。
**したがって、外部の接続先で当面効く歯止めは、向こうのキーごとの上限だけである。**

**外部の接続先の上限は、向こうのキーに持たせる。** OpenRouter は
キーごとに `limit` (USD) を設定できる。`limit_reset` (daily / weekly / monthly)
も設定できる (OpenRouter の確認メモの 6)。justic の外で効くので、justic の不具合
(二重に走る、上限の数え間違い) でも超えない。justic はこれを設定しないし、
読みにも行かない (12.2 と同じ理由)。

残高の照会 (`GET /api/v1/key` の `limit_remaining`) は justic から引かない。
画面や `/api/stats` に費用を出すかは未決 (`EP-04`)。

**1回あたりいくらかは、まだ言わない**。 公表されている単価は
`google/gemini-3.8-flash` で入力 $0.75 / 1M、出力 $3.75 / 1M (OpenRouter の確認メモの 4-4)。
1回の観点でどれだけのトークンを使うかは測っていないので、掛け算をしない。
`review_aspects.cost` が数件溜まったところで数える。

## 16. 確かめ方

18080 / 18090 / openrouter.ai に要求を送らずに確かめる。

### 16.1 手元に OpenAI 互換の応答を返すだけのサーバーを立てる

`web/test/fake-llm.js` を置く。node の `http` だけで書き、依存を増やさない。
`POST /v1/chat/completions` を受けて、**受け取った要求をファイルに書き、
決め打ちの JSON を返す**。 `JUSTIC_ENDPOINTS` に試験用の設定を指し、
`base_url` をこのサーバーに向ける。

確かめられること。

| 確かめること | 見る場所 |

| 設定した `temperature` / `max_tokens` / `thinking` / `response_format` / `provider` が要求本文に入るか | 書き出した要求 |

### 16.2 キーファイルの権限の検査

試験用のディレクトリに 0644 のキーファイルを作り、レビューが走らずに
`chmod 600` を促す文言で落ちることを確かめる (5.4)。

### 16.3 外部の接続先を選ばない限り外に出ないこと

**担保の程度を正直に書く。**

| 方法 | 担保 |
|---|---|
| justic が `fetch` を呼ぶ場所を数える | **ある。** `web/` を `fetch(` で検索すると、サーバー側は 5 箇所: `llm.js` 68行 (宛先は接続先の `base_url`)、`github.js` 33行と 140行、`auth.js` 95行と 112行 (どれも `github.com` / `api.github.com` で固定)。**宛先が設定で変わるのは `llm.js` の1箇所だけ。** `public/app.js` の3箇所はブラウザから justic 自身を呼ぶもの。読んで確かめる担保であって、走らせて確かめる担保ではない |
| 外部の接続先を設定に置いたまま `local` で走査し、要求が向こうに出ないこと | **半分。** 16.1 のサーバーに `local` を向ければ、`local` の走査がそこへ行くことは確かめられる。openrouter.ai に出ていないことは、こちらから確かめられない |
| ネットワーク側で外向きを止めて走らせる | **無い。** この環境では試していない |

### 16.4 確かめられないもの

- **OpenRouter が実際にこの要求を受け付けるか。** 要求を送らないので分からない。

- **手元の llama-server が `chat_template_kwargs` を見て思考を止めるか。**
