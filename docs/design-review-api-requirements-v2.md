# 設計書レビューAPI 要件

草案 [design-review-api-requirements.md](design-review-api-requirements.md) を、調査で裏の取れた事実に合わせて書き直したもの。草案は変更していない。調査日は 2026-09-05。

草案からの差分は3点。

| 差分 | 内容 |
|---|---|
| L1 の中身 | textlint の各プリセットが実際に何を検出するかを、公開 README で確認した結果に置き換えた |
| 直訳調の担当 | L1 から L4 に移した。プロンプトでもルールでも判定できないため（3.2 節） |
| L3 の粒度 | 観点を1本に絞って評価まで通す形にした |

## 1. 目的

生成モデルが書いた Markdown の設計書をレビューし、指摘を構造化データとして返す API を作る。

検出対象は2つ。**設計内容の欠陥**と**直訳調の日本語**。書いたモデル自身に読み返させても、どちらも検出できない。前者は欠陥を含む文書がモデルにとって自然に見えるため、後者はその文体がモデルの既定であるため。検査は生成とは独立した経路に置く。

## 2. 前提

| ID | 内容 | 状態 |
|---|---|---|
| PRE-01 | 入力は Markdown の設計書 | 確定 |
| PRE-02 | レビュー範囲は文体の癖と設計内容の妥当性の両方 | 確定 |
| PRE-03 | 実装は Node。textlint をライブラリとして組み込む | 確定 |
| PRE-04 | 設計書の書き手は生成モデル | 確定 |
| PRE-05 | 対象文書は日本語 | 確定（草案 OPEN-04 を解消） |
| PRE-06 | Claude 本体のチューニングは対象外 | 確定（理由は9章） |

## 3. 検出対象

### 3.1 設計内容の欠陥

判定基準を言語化できる。観点ごとに問いの形にすれば、生成モデルが答えられる。

| ID | 観点 | 問いの形 |
|---|---|---|
| D-01 | 異常系の未定義 | 不正な入力に対する振る舞いを定義しているか |
| D-02 | 権限と認可 | 誰が実行できるかを定義しているか |
| D-03 | 同時実行と冪等性 | 二重実行の結果を定義しているか |
| D-04 | 移行と後方互換 | 既存データの扱いを定義しているか |
| D-05 | 非機能の数値 | 性能と容量に数値があるか |
| D-06 | 代替案と却下理由 | 選ばなかった案とその理由があるか |
| D-07 | 監視とロールバック | 失敗を検知して戻す手順があるか |
| D-08 | 章をまたぐ矛盾 | 同じ対象を別の章が別に定義していないか |

D-01 の具体例。次の一文は文体としては問題がないが、不正な入力に対する振る舞いを定義せず結果だけを書いている。

> httpリクエストのJSONに不備があると、プロセスは黙って壊れる

**この種の記述が検出できることを、最初の受け入れ条件とする。**

### 3.2 直訳調の日本語

判定基準を言語化できない。ここが草案および前版との最大の差。

| | 設計内容の欠陥 | 直訳調 |
|---|---|---|
| 基準 | 言語化できる | できない。認識はできる |
| 性質 | 有無の判定 | 程度の判定。どの文も多少は該当する |
| 手段 | 観点別プロンプト（L3） | **学習した分類器（L4）** |

プロンプトが機能しない理由は2つ。

1. **判定する側が同じ癖を持つ。** 生成モデルの既定の文体が直訳調であるため、基準を持てない。
2. **閾値の判断である。** パターンの有無ではなく程度を問うので、スコアが要る。プロンプトは閾値を持てない。

パターンとして書ける一部は L1 で取る（5章）。ただしそれは全体の一部であり、網羅を意図しない。

## 4. 層の構成

| 層 | 担当 | 手段 |
|---|---|---|
| L1 | 直訳調のうち決定的に書ける分、表記の統一 | textlint |
| L2 | 設計内容のうち決定的に取れる分 | 抽出パーサと突合 |
| L3 | 設計内容の欠陥（D-01〜D-08） | 観点別の LLM パス |
| L4 | 直訳調の判定、L3 の指摘の採否 | 学習した分類器 |

決定的に取れるものを L1 と L2 で先に取り、残りだけを L3 と L4 に回す。

## 5. L1（textlint）

### 5.1 調査結果

| プリセット | 直訳調に効くか |
|---|---|
| `@textlint-ja/textlint-rule-preset-ai-writing` | 5ルール中 `ai-tech-writing-guideline` のみ。他は箇条書きの体裁、誇張、太字強調、コロンの英語的用法 |
| `textlint-rule-preset-ja-technical-writing` | **効く。** `ja-no-redundant-expression` の6辞書が中心 |
| `textlint-rule-preset-JTF-style` | **効かない。** 名前に反して内容は表記の規定。採らない |

`preset-ai-writing` は設計方針として「表現を縛るのではなく、構造を縛る」を掲げている。草案 L1-05 はこの方針を写したものだが、直訳調は表現の側にあるため、L1 の担当範囲を狭める方向に働く。3.2 節の整理により、L1-05 は維持したうえで直訳調の本体を L4 に移す。

`ja-no-redundant-expression` の辞書。

| 辞書 | パターン | 対応する英語 |
|---|---|---|
| dict1 / dict2 | すること[助詞](不)可能 / すること[助詞]できる | can / cannot |
| dict3 / dict4 | であると言えます / であると考えている | it can be said / it is considered |
| dict5 / dict6 | [サ変名詞]を行う / [サ変名詞]を実行 | perform, do / execute |

dict5 と dict6 には既定の除外があり、`[ァ-ヶ]+を.?行[ぁ-ん]` などが通る。**「バリデーションを行う」は既定で検出されない。** 設計書ではこの形が多いため調整が要る（L1-08）。

`sentence-length`（100字）、`max-ten`（読点3つ）、`no-doubled-joshi` は、訳し下した長文に効く。

### 5.2 要件

| ID | 要件 |
|---|---|
| L1-01 | `createLinter` と `loadTextlintrc` で組み込み、`lintText(text, virtualPath)` で文字列を直接検査する。API はファイルを持たない |
| L1-02 | `@textlint-ja/textlint-rule-preset-ai-writing` を有効にする |
| L1-03 | prh に独自の表記辞書を持つ。表記ゆれと語彙の癖を集約する |
| L1-04 | 自作ルール（mdast 走査）で、必須セクションの欠落、TBD と TODO の残存、定量化されていない形容、見出しレベルの飛び、言語指定のないコードブロックを検出する |
| L1-05 | ルールは表現の禁止より構造の検査を優先する |
| L1-06 | プロファイル切り替えは `configFilePath` の差し替えで行う |
| L1-07 | `textlint-rule-preset-ja-technical-writing` を有効にする |
| L1-08 | `ja-no-redundant-expression` の dict5 と dict6 について、カタカナのサ変名詞を除外から外す |
| L1-09 | プリセットとルールのバージョンを固定し、評価結果と組で記録する |

L1-04 の「必須セクションの欠落」は、設計書テンプレートの定義に依存する（OPEN-02）。**欠落は L3 に頼らず決定的に検出でき、誤検知が出ないため blocking にできる。** レビュー負担の低減に最も直接効くのはここになる。

## 6. L2（抽出・突合）

| ID | 要件 |
|---|---|
| L2-01 | コードブロックから OpenAPI、JSON Schema、SQL DDL、Mermaid を抽出する |
| L2-02 | 抽出物を既存パーサで検証する（swagger-parser、ajv、node-sql-parser、mermaid） |
| L2-03 | 抽出物どうしの名前を突き合わせる。ER 図のエンティティ、DDL のテーブル、OpenAPI のスキーマ |
| L2-04 | 要件 ID、設計項目、テスト観点の相互参照のリンク切れを検出する |
| L2-05 | **OpenAPI に 4xx と 5xx の定義があるかを検査する。** D-01 のうち決定的に取れる分 |
| L2-06 | L2 は textlint のルールとして実装しない。非同期処理と外部依存が入るため、mdast を共有する別モジュールとする |

草案 L2-03 は「本文の表の項目名」も突合対象に含めていた。表の列名は自由記述であり、L2 は blocking する層であるため、対象から外した。

## 7. L3（設計内容の観点別パス）

| ID | 要件 |
|---|---|
| L3-01 | 観点ごとに独立したパスとして実行する。1プロンプトに複数観点を並べない |
| L3-02 | 観点は D-01〜D-08。**初版は D-01 の1本に絞り、評価まで通してから増やす** |
| L3-03 | 出力は JSON 固定。zod スキーマで検証する |
| L3-04 | finding ごとに原文の引用と行番号を必須にする |
| L3-05 | 引用が原文に存在しない finding は機械的に破棄する |
| L3-06 | 空配列を許容する。few-shot に「該当なし」の例を含める |
| L3-07 | 本文をプロンプト先頭に置き、プロンプトキャッシュを効かせる。メッセージの並び順を固定する |
| L3-08 | モデル ID は設定ファイルに出し、評価結果と組で記録する |
| L3-09 | 観点は判定可能な問いの形で書く。「レビューせよ」ではなく「定義しているか」を問う |

D-01 のプロンプトの骨格。

```
この設計書は、不正な入力に対する振る舞いを定義しているか。
定義せずに結果だけを書いている箇所を、原文の引用と行番号を付けて挙げよ。
該当がなければ空配列を返せ。
```

モデル割当（提案値）

| 用途 | モデル |
|---|---|
| 観点パスの大半 | Sonnet 5 |
| D-08（章をまたぐ矛盾）、設計判断の妥当性 | Opus 5 |
| finding の正規化と重複マージ | Haiku 4.5、または決定的処理で代替 |
| 評価セットの裁定 | Fable 5.1 |

## 8. L4（学習した分類器）

役割が2つある。草案では後者だけだった。

### 8.1 直訳調の判定

| ID | 要件 |
|---|---|
| L4-01 | modernbert-ja（130m または 310m）に分類ヘッドを付けた二値分類器とする |
| L4-02 | **学習データは出自からラベルを付ける。** 正例は生成モデルが日本語で書いた文書、負例は日本語で書かれた技術文書。人手のアノテーションを要しない |
| L4-03 | 判定と説明を分ける。**分類器がスコアを出し、指摘文の生成は LLM が担当する。** 判定を LLM にさせない |
| L4-04 | スコアの閾値を severity にマップし、プロファイルの設定項目として露出する |
| L4-05 | ONNX に変換し `onnxruntime-node` から呼ぶ。推論は CPU で行い、別サービスを立てない |

正例は検出対象そのもの（生成モデルが書いた設計書）から取る。機械翻訳した日本語は分布が異なるため使わない。前者は英語的な言い回しを日本語として再構成したもの、後者は原文の構造を保ったまま置き換えたもので、別物になる。

### 8.2 L3 の指摘の採否

| ID | 要件 |
|---|---|
| L4-06 | 入力は観点 ID、指摘文、引用、前後の段落、L1 と L2 の同時発火状況。出力は採用確率 |
| L4-07 | 学習データは採否ログ。**利用者が1人の場合、蓄積速度が実現性を決める**（OPEN-01） |
| L4-08 | 8.1 とは別モデルとする。教師信号の出自が異なる |

記録する項目

| 項目 | 用途 |
|---|---|
| review_id | 突合 |
| finding 本体 | 入力特徴 |
| 生成に使ったモデル ID とプロンプトのバージョン | 世代比較 |
| 原文の該当位置 | 入力特徴、幻覚判定 |
| 採否ラベル | 教師信号 |
| 採用時の修正後テキスト | 検索と将来の生成学習 |

**記録していない期間のデータは後から復元できない。** 8.2 を後回しにする判断をしても、記録項目は初版から入れる。

## 9. severity 方針

| 対象 | 初期値 | blocking |
|---|---|---|
| L2 の外部パーサ検証、名前の突合、4xx/5xx の欠落 | error | する |
| L1-04 の必須セクションの欠落 | error | する |
| L1 のその他の構造チェック | warn | しない |
| L1 の文体チェック | warn | しない |
| L4 の直訳調スコア | 閾値に応じて warn / info | しない |
| L3 の指摘 | info | しない |

誤検知で blocking すると使われなくなるため、blocking は決定的な層に限る。

**文体が通ったことを、設計が妥当であることと読ませない。** L1 のみが通った状態と、L3 まで通した状態を応答で区別する。前者を「レビュー済み」と表示しない。

## 10. API

| ID | 要件 |
|---|---|
| API-01 | `POST /reviews` は非同期。review_id を返す |
| API-02 | `GET /reviews/:id` で状態と findings を返す |
| API-03 | L1 と L2 のみの同期モードを持つ |
| API-04 | finding は層をまたいで同一スキーマに揃える |
| API-05 | SARIF 形式への変換を用意する |
| API-06 | 本文の hash で結果をキャッシュする |
| API-07 | 抑制コメント（`<!-- docreview-disable-next-line rule-id -->`）に対応する |
| API-08 | ルールセットと severity の上書きを YAML のプロファイルとして外出しする |
| API-09 | **応答に、実行した層を含める。** どこまで検査したかを利用者が判別できるようにする |

finding スキーマ

```ts
{
  rule_id: string;      // 例: "struct/missing-section", "design/undefined-error-path"
  layer: "L1" | "L2" | "L3" | "L4";
  severity: "error" | "warn" | "info";
  location: { line: number; column: number; end_line?: number; end_column?: number };
  message: string;
  evidence?: string;    // L3では必須。原文に存在することを検証する
  suggestion?: string;
  confidence?: number;  // L3およびL4が付与
}
```

## 11. 評価

| ID | 要件 |
|---|---|
| EV-01 | ゴールデンセットとして過去の設計書 20 から 50 本に人手の指摘を付ける |
| EV-02 | L3 は観点ごとに recall と precision を分けて測る。全体で1スコアにしない |
| EV-03 | L4 の分類器は precision、recall、PR-AUC で測る |
| EV-04 | プロンプトまたはモデルの変更時に CI でゴールデンセットを流す |
| EV-05 | 評価結果にモデル ID とプロンプトのバージョンを紐付けて保存する |
| EV-06 | **初版の受け入れ条件は D-01 のみ。** 3.1 節の例文を含む文書を検体に入れる |

完全な検出は目標にしない。人が毎回頭の中で回している確認を機械に移すことが目的であり、D-01 を高い precision で相当数拾えれば効果が出る。

## 12. 未決事項

| ID | 項目 | 影響する箇所 |
|---|---|---|
| OPEN-01 | 利用者は1人か複数か | 8.2 の実現性。採否ログの蓄積速度 |
| OPEN-02 | 必須セクションの定義（設計書テンプレート） | L1-04。**決定的に検出でき blocking できるため、優先度が最も高い** |
| OPEN-03 | 呼び出し元（CI、CLI、エディタ、MCP 経由の AI ツール） | API-01 から API-03 の形、認証の要否 |
| OPEN-04 | 認証とマルチテナントの要否 | API 全体 |
| OPEN-05 | 既存のレビュー履歴の有無 | 8.2 の初期データ、EV-01 の作りやすさ |
| OPEN-06 | 1文書あたりの許容レビュー時間 | L3 の観点数、同期と非同期の切り分け |
| OPEN-07 | 稼働環境（ローカル、自前サーバ、クラウド） | L4 の推論配置、キューの構成 |
| OPEN-08 | コスト上限 | L3 のモデル割当と観点数 |
| OPEN-09 | 自動修正（fix）まで行うか | textlint の fixer を使うかどうか |
| OPEN-10 | 8.1 の学習データをどこから集めるか | L4-02。手元の既存文書の量による |

草案 OPEN-04（日本語のみか英語混在か）は PRE-05 として確定した。

**テンプレートを書き手にも渡すかどうかは、OPEN-02 に含めて判断する。** 必須セクションを定義したうえで生成側にも渡せば、異常系が節として表に出る。検出と予防で往復が1回減る。
