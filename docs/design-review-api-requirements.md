# 設計書レビューAPI 要件整理

会話で決まった内容をまとめたもの。確定しているのは「レビュー範囲」と「実装スタック」の2点。それ以外は提案値であり、変更してよい。確認が必要な項目は10章にまとめた。

## 1. 目的

生成モデルが書いたMarkdownの設計書を、機械的な検査とLLMによる検査の2系統でレビューし、指摘を構造化データとして返すAPIを作る。

生成モデルには検討を経ずに出る表現の癖があり、書いたモデル自身に読み返させても検出できない。検査は生成とは独立した経路で行う必要がある。

## 2. 前提

| ID | 内容 | 状態 |
| --- | --- | --- |
| PRE-01 | 入力はMarkdownの設計書 | 確定 |
| PRE-02 | レビュー範囲は文体の癖と設計内容の妥当性の両方 | 確定 |
| PRE-03 | 実装はNode。textlintをライブラリとして組み込む | 確定 |
| PRE-04 | 設計書の書き手は生成モデル | 確定 |
| PRE-05 | Claude本体のチューニングは提供がないためスコープ外 | 確定 |

## 3. 決定層（L1・textlint）

| ID | 要件 |
| --- | --- |
| L1-01 | `createLinter` と `loadTextlintrc` で組み込み、`lintText(text, virtualPath)` で文字列を直接検査する。APIはファイルを持たない |
| L1-02 | `@textlint-ja/textlint-rule-preset-ai-writing` を有効にする |
| L1-03 | prh に独自の表記辞書を持つ。生成モデルの癖の語彙はここに集約する |
| L1-04 | 自作ルール（mdast走査）で、必須セクションの欠落、TBDとTODOの残存、定量化されていない形容、見出しレベルの飛び、言語指定のないコードブロックを検出する |
| L1-05 | ルールは表現の禁止より構造の検査を優先する。禁止語は言い換えで回避されるが、構造は回避できない |
| L1-06 | プロファイル切り替えは `configFilePath` の差し替えで行う |

## 4. 抽出・突合層（L2）

| ID | 要件 |
| --- | --- |
| L2-01 | コードブロックから OpenAPI、JSON Schema、SQL DDL、Mermaid を抽出する |
| L2-02 | 抽出物を既存パーサで検証する（swagger-parser、ajv、node-sql-parser、mermaid） |
| L2-03 | 抽出物どうしの名前を突き合わせる。ER図のエンティティ、DDLのテーブル、OpenAPIのスキーマ、本文の表の項目名 |
| L2-04 | 要件ID、設計項目、テスト観点の相互参照のリンク切れを検出する |
| L2-05 | L2はtextlintのルールとして実装しない。非同期処理と外部依存が入るため、mdastを共有する別モジュールとする |

設計内容の妥当性のうち、機械的に確定できる部分をここで拾う。L3に回すのはここで拾えないものだけとする。

## 5. LLM層（L3）

| ID | 要件 |
| --- | --- |
| L3-01 | 観点ごとに独立したパスとして実行する。1プロンプトに複数観点を並べない |
| L3-02 | 観点の初期案は、異常系の未定義、権限と認可、同時実行と冪等性、移行と後方互換、非機能の数値、代替案と却下理由、監視とロールバック、章をまたぐ矛盾 |
| L3-03 | 出力はJSON固定。zodスキーマで検証する |
| L3-04 | finding ごとに原文の引用と行番号を必須にする |
| L3-05 | 引用が原文に存在しない finding は機械的に破棄する |
| L3-06 | 空配列を許容する。few-shot に「該当なし」の例を含める |
| L3-07 | 本文をプロンプト先頭に置き、プロンプトキャッシュを効かせる。メッセージの並び順を固定する |
| L3-08 | モデルIDは設定ファイルに出し、評価結果と組で記録する |

モデル割当（提案値）

| 用途 | モデル |
| --- | --- |
| 観点パスの大半 | Sonnet 5 |
| 章をまたぐ矛盾、設計判断の妥当性 | Opus 5 |
| findingの正規化と重複マージ | Haiku 4.5、または決定的処理で代替 |
| 評価セットの正解づくり、判定が割れたときの裁定 | Fable 5 |

## 6. チューニング層（L4）

| ID | 要件 |
| --- | --- |
| L4-01 | チューニング対象はClaude以外のモデルとする |
| L4-02 | 判定器はmodernbert-ja（130mまたは310m）に分類ヘッドを付けて学習する |
| L4-03 | 判定器の入力は観点ID、指摘文、引用、前後の段落、L1とL2の同時発火状況。出力は採用確率 |
| L4-04 | 判定器はONNXに変換し onnxruntime-node から呼ぶ。推論はCPUで行い、別サービスを立てない |
| L4-05 | 文書種別の分類器で観点セットを切り替える（既存資産が数百本ある場合） |
| L4-06 | 類似の過去指摘の検索に ruri-v3 系 embedding を使う。初期は学習なし |
| L4-07 | 判定器の閾値を severity にマップし、プロファイルの設定項目として露出する |

学習データとして記録する項目

| 項目 | 用途 |
| --- | --- |
| review_id | 突合 |
| finding本体 | 入力特徴 |
| 生成に使ったモデルIDとプロンプトのバージョン | 世代比較 |
| 原文の該当位置 | 入力特徴、幻覚判定 |
| 採否ラベル | 教師信号 |
| 採用時の修正後テキスト | 検索と将来の生成学習 |

記録していない期間のデータは後から復元できない。

## 7. API

| ID | 要件 |
| --- | --- |
| API-01 | `POST /reviews` は非同期。review_id を返す |
| API-02 | `GET /reviews/:id` で状態と findings を返す |
| API-03 | L1のみの同期モードを持つ |
| API-04 | finding は層をまたいで同一スキーマに揃える |
| API-05 | SARIF 形式への変換を用意する |
| API-06 | 本文のhashで結果をキャッシュする |
| API-07 | 抑制コメント（`<!-- docreview-disable-next-line rule-id -->`）に対応する |
| API-08 | ルールセットと severity の上書きをYAMLのプロファイルとして外出しする |

finding スキーマ

```ts
{
  rule_id: string;      // 例: "struct/missing-section", "spec/openapi-invalid"
  layer: "L1" | "L2" | "L3";
  severity: "error" | "warn" | "info";
  location: { line: number; column: number; end_line?: number; end_column?: number };
  message: string;
  evidence?: string;    // L3では必須。原文に存在することを検証する
  suggestion?: string;
  confidence?: number;  // L3およびL4の判定器が付与
}
```

## 8. severity方針

| 対象 | 初期値 | blocking |
| --- | --- | --- |
| L2の外部パーサ検証と名前の突合 | error | する |
| L1の構造チェック | error または warn | 要検討 |
| L1の文体チェック | warn | しない |
| L3の指摘 | info | しない |

誤検知でblockingすると使われなくなるため、blockingは決定的な層に限る。

## 9. 評価要件

| ID | 要件 |
| --- | --- |
| EV-01 | ゴールデンセットとして過去の設計書20から50本に人手の指摘を付ける |
| EV-02 | L3は観点ごとに recall と precision を分けて測る。全体で1スコアにしない |
| EV-03 | L4の判定器は precision、recall、PR-AUC で測る |
| EV-04 | プロンプトまたはモデルの変更時にCIでゴールデンセットを流す |
| EV-05 | 評価結果にモデルIDとプロンプトのバージョンを紐付けて保存する |

## 10. 未決事項

| ID | 項目 | 決まらないと影響する箇所 |
| --- | --- | --- |
| OPEN-01 | 利用者は1人か複数か | L4の実現性。採否ログの蓄積速度が学習の可否を決める |
| OPEN-02 | 呼び出し元（CI、CLI、エディタ、MCP経由のAIツール） | API-01からAPI-03の形、認証の要否 |
| OPEN-03 | 認証とマルチテナントの要否 | API全体 |
| OPEN-04 | 対象文書は日本語のみか、英語混在か | L1のルールセット |
| OPEN-05 | 既存のレビュー履歴の有無 | L4の初期データ、EV-01の作りやすさ |
| OPEN-06 | 必須セクションの定義（設計書テンプレート） | L1-04が書けない |
| OPEN-07 | 1文書あたりの許容レビュー時間 | L3の観点数、同期と非同期の切り分け |
| OPEN-08 | 稼働環境（ローカル、自前サーバ、クラウド） | L4の推論配置、キューの構成 |
| OPEN-09 | コスト上限 | L3のモデル割当と観点数 |
| OPEN-10 | 自動修正（fix）まで行うか | textlintのfixerを使うかどうか |
| OPEN-11 | L4を最初から作るか、後から足すか | 初期の記録項目（6章）を入れるかどうか |
