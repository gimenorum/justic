## 解くべき問題

### 非同期化 (要件 `API-01`)

`API-01`「`POST /reviews` は非同期。review_id を返す」は決定済みで未実装。
現状の `/api/reviews/github/branch` は全ファイルを `await` で逐次処理し、
1つの JSON を返す**同期 HTTP**。`JUSTIC_L3_TIMEOUT_MS` の既定は 120 秒。

決めること: ジョブの保存先、worker の形、状態遷移、進捗の取得口、取り消し、
`app.js` が `state.reviews` にメモリ保持している構造の置き換え。

**「10分を超えたら非同期に切り替える」は実装できない。** 同期 HTTP は
応答を返し始める前に同期か非同期かが決まる。最初から非同期にするか、しないかである。

### 本文 hash によるキャッシュ (要件 `API-06`)

`API-06`「本文の hash で結果をキャッシュする」は決定済みで未実装。
`documents.sha256` は既にある。走査は何度でも回す道具なので、
変更のないファイルを0回にできる。

**着手する前に鍵が要る。** 実データで `reviews.prompt_version` は 43 行すべて NULL。
`server.js` は `createReview` に `promptVersion` を渡していない。
`l3_model_id` は `MODEL || "(サーバー既定)"` なので、環境変数未設定なら全件同じ文字列。
01 の `review_aspects` が `model_id` と `prompt_version` を持つので、そこが前提になる。

決めること:

- **当たったときに何を返すか。** 新しい `review` を作って `findings` を複製すると
  `labeled_findings` に同じ指摘が2度入り、教師データが重複する。
  古い `review_id` を返すと、その review の `layers` / `source_ref` / `in_diff` は
  前回の走査のもので、画面と食い違う (PR 走査では `in_diff` が別の PR の値になる)
- 無効化の条件 (プロンプト改訂、textlint のバージョン、要件 `L1-09`)

**優先順に注意。** R-03 が壊れるのは初回走査と変更のあったファイル、つまり
キャッシュミスになる場面である。キャッシュは常用時の緩和にはなるが、
最悪待ち時間を有界にはしない。それができるのは非同期化のほうである。

### 走査 (scan) という単位

`reviews` を束ねる行が無い。`server.js` の `reviewOne` は 1ファイル 1 review。
「1走査あたりの上限」「実行中の同じ走査があればその ID を返す」「呼び出し回数の
事前表示」「走査した文書 120 本」— これらはすべて複数 review をまたぐ単位を要求する。

`scans (id, repo, ref, aspect_set, model_id, prompt_version, started_at,
finished_at, status, call_count)` と `reviews.scan_id` が要る。

### 冪等性

走査は冪等でない。`upsertDocument` は hash で重複を防ぐが、`reviews` と `findings` は
毎回新規。**同じブランチを2回走査すると findings が倍になり、二重クリックで
呼び出しが2倍になる。** `stats()` の「提示した指摘」も倍になる。

実行中の同じ鍵の走査があれば新規に始めず、その走査を返す。
鍵は `(repo, ref, 観点集合, モデル, プロンプト版)`。

### 上限と数値

決まっていない。要件 `OPEN-06` (許容レビュー時間) と `OPEN-08` (コスト上限) が
決まらないと暫定にしかならない。

**上限は警告ではなく、超えたら止まるものとする。** ただし単位が決まっていない
(00 の 4.3) ので、03 と歩調を合わせる。

前の版で「同時実行数1・タイムアウト120秒・上限200回・目標10分」と書いたが、
逐次で200回を600秒に収めるには1回平均3秒が要り、**タイムアウト1回で予算の20%を使う。**
両立しない。

### 並列化とプロンプトキャッシュ

`llm.js` は `SYSTEM + 本文` を共通接頭辞にし、末尾の観点だけを変える (要件 `L3-07`)。
同じ本文に対して観点を逐次に投げれば、2回目以降は本文の prefill がキャッシュに当たる。

**ファイル間を並列にするとこれが壊れる。** 異なる本文が同時に走って接頭辞が入れ替わる。

ただしこの効果の大きさは**未確認**である。推論サーバーの接頭辞キャッシュの有無・容量・
失効条件を読んでいない。**確認してから対策として数えること。**
また 03 が単位を段落にすると、本文が段落ごとに変わるのでこの効果は消える。

### 失敗したとき

| 失敗 | 決めること |
|---|---|
| 推論サーバーに繋がらない | L1 の結果だけ返す。理由を画面に出す |
| 観点1本がタイムアウト | その観点だけ落とす。他は返す |
| JSON が壊れて解釈できない | 「該当なし」と区別する。実装変更は 01 の11章 |
| **コンテキスト長を超えた** | 入力を切らずに失敗させる。**切り詰めて「指摘なし」を返さない** |
| GitHub のレート制限 | 走査を止め、処理済みを保存し、残りを一覧で出す |
| 走査の途中で落ちた | `reviews.finished_at` が NULL。集計から除外する (01 の 7.3) |

**どの場合も「検査した」と「指摘が無かった」を混同させない。**
