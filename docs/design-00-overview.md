# 追加設計の地図と、共通の決定

いま動いているものへの追加設計を4本に分ける。この文書はその地図と、
4本すべてが参照する共通の決定を持つ。2026-09-06。

要件は [design-review-api-requirements-v2.md](design-review-api-requirements-v2.md) (以下「要件」)。
草案を指すときは「草案」と明記する。

## 1. 解こうとしている問題

| ID | 問題 | 担当 |
|---|---|---|
| P-01 | 検査対象が Markdown に限られる。ソースの日本語コメントが検査されない | 03 入力 |
| P-02 | 文書の種類によらず同じ問いを当てている | 04 観点 |
| P-03 | **未検知を記録できない。recall の分母が作れない** | 01 測定 |

## 2. なぜ分けるか

一度は1本の設計書に書いたが、2回のレビューで3つのことが分かった。

**決められる単位が違う。** 非同期化とキャッシュは、何を検査するかと無関係に決まる。
共通観点の本数は、実行基盤と無関係に決まる。1本に混ざっていると片方が決まらないと
もう片方も止まる。

**レビューが「別設計が要る」と3箇所で指摘した。** 非同期化と hash キャッシュは
この規模では決められない、API の章が無い、走査を束ねる表が無い。

**作る順序が、書いた順序と逆だった。** 最初の版はコメント検査を先頭に置いたが、
それが最も高くつき、最も何も解かない選択だった。

## 3. 依存の順序

| # | 文書 | 呼び出し回数への影響 | 何を解くか | 依存 |
|---|---|---|---|---|
| 02 | [実行基盤](design-02-runtime.md) | **減らす** | 観点を増やせるようにする | 無し |
| 01 | [測定](design-01-measurement.md) | 増やさない | **P-03。段階導入の門番** | 無し |
| 03 | [入力の拡大](design-03-input.md) | **×18** (10ファイル → 184段落) | P-01 | 02 |
| 04 | [観点](design-04-aspects.md) | ×観点数 | P-02 | 02 と 01 |

**測定 (01) から書く。** 依存が無く、最大リスク R-04 (未検知の登録が使われず
recall が永久に測れない) に最も早く当たり、他の3本の門番を作る。
Markdown だけ・`D-01` だけ・いまの画面への追加だけで始められる。

## 4. 共通の決定

4本が同じ前提に立つよう、ここで決める。**各文書はこれを再定義しない。**

### 4.1 観点 ID の台帳

`findings.aspect_id`、`human_annotations.aspect_id`、`review_aspects.aspect_id`、
`annotation_completions.aspect_id` が同じ ID 空間を参照する。
自由記述の `text` にすると、表記ゆれ (`D-1` / `d-01`) 1件で結合が静かに外れ、
**recall が下がったように見える。**

`aspects` 表を作り、4箇所すべてから外部キーを張る (6章)。

要件 `L3-02` で `D-01`〜`D-08` は確定済み。**`D-07` (監視とロールバック) と
`D-08` (章をまたぐ矛盾) は既存の意味のまま残す。** 新設は `D-09` 以降。

| 接頭辞 | 用途 |
|---|---|
| `D-01`〜`D-08` | 設計書。要件で確定済み。変更しない |
| `D-09` 以降 | 設計書の新設分 |
| `C-*` | 全文書に当てる共通観点 |
| `R-*` `N-*` `A-*` `Q-*` `O-*` | README / CONTRIBUTING / ADR / 要件定義 / 運用手順 |
| `K-*` | ソースコードのコメント |

**観点集合を `D-*` の外へ広げるには、要件 `L3-02`
(「観点は D-01〜D-08」「初版は D-01 の1本に絞り、評価まで通してから増やす」) の
改訂が要る。** 04 で扱う。

### 4.2 文書の同一性

`documents` は本文の sha256 で一意化されている (`db.js` の `upsertDocument`)。
**この道具の目的は文書を直させることなので、注釈を付けた文書は直る。**
直った瞬間に hash が変わって別行になり、注釈も完了印も旧行に取り残される。

決定を3つ置く。

**(a) `documents` の hash 一意化は変えない。** 既存の全経路が依存している。

**(b) 論理的な同一性を別に持つ。** `document_keys (repo, path)` を導入し、
`documents` から参照する。「同じファイルの別の版」を辿れるようにする。
貼り付け経路には repo も path も無いので NULL 可とし、その場合は
版をまたぐ追跡ができないことを受け入れる。

**(c) 注釈は版に付ける。自動で引き継がない。** 文書が直ったとき、
旧版の注釈を新版へ引き継ぐかは**利用者が確認する**。`quoted_text` の
一致による再アンカーは候補の提示にとどめ、無言で移さない。

理由: 直した結果その指摘が解消されたのか、位置がずれただけなのかは
機械的に判定できない。無言で移すと、既に直った欠陥が recall の分母に残り続ける。

### 4.3 検査の単位

**「1回の LLM 呼び出しが、どの範囲のテキストを見るか」を単位と呼ぶ。**

| 入力 | 単位 | 呼び出し回数 |
|---|---|---|
| Markdown | 1ファイル = 1単位 | ファイル数 × 観点数 |
| ソースのコメント | **03 で決める。段落か、ファイル分をまとめたものか** | 単位数 × 観点数 |

最初の版は「ファイル数 × 観点数」で数えて桁を外した。cmdmuse の Go 19ファイルには
**日本語コメント段落が 184** あり、段落を単位にすると観点5本で 920 回になる。

**03 が単位を決めるまで、コメントの呼び出し回数を見積もらない。**
02 の上限もこの単位に合わせる。

## 5. 用語

| 語 | 意味 |
|---|---|
| 走査 (scan) | 1回の操作で走る複数のレビューの束。ブランチ走査で N ファイルなら N レビュー |
| レビュー (review) | 1文書に対する1回の検査。`reviews` の1行 |
| 単位 | 4.3 |
| 観点 | LLM に投げる1つの問い。`aspects` の1行 |
| 指摘 (finding) | システムが出したもの。`findings` の1行 |
| 注釈 (annotation) | 利用者が付けたもの。**システムの見落とし。`findings` には入れない** |
| 全数注釈 | ある文書のある観点について、全単位を見て判断し終えた状態 |

## 6. `aspects` 表

4.1 の台帳。01 の移行 (`004`) で作る。

```sql
create table aspects (
    id          text primary key,          -- 'D-01', 'C-01', 'K-03' …
    prefix      text not null,             -- 'D', 'C', 'K' …
    title       text not null,
    question    text not null,             -- LLM に投げる問い
    applies_to  text[] not null,           -- 適用する文書種別。'*' で全部
    unit        text not null default 'document'
                check (unit in ('document', 'span')),
    added_at    timestamptz not null default now(),
    retired_at  timestamptz                -- 廃止しても行は消さない。過去の記録が参照する
);
```

**廃止しても行を消さない。** 過去の `findings.aspect_id` と
`annotation_completions.aspect_id` が参照するため。

初期データは `D-01` の1件のみ。`llm.js` の `ASPECTS` 配列をこの表に移す。
04 が観点を足すときはこの表に行を足す。
