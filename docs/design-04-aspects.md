## 解くべき問題

### 要件 `L3-02` の改訂

`L3-02` は「観点は D-01〜D-08」「**初版は D-01 の1本に絞り、評価まで通してから
増やす**」。`llm.js` のコメントにも同じことが書いてある。

観点集合を `D-*` の外へ広げるには、この要件の改訂が要る。
段階に分けても、各段に評価の条件が無ければ要件を満たさない。
**「一度に増やさない」は `L3-02` の要求ではない。要求は「増やす前に評価を通す」。**

### 段階と門番

各段の進行条件を、01 の `annotation_completions` の単位で書く。

主キーは `(document_id, aspect_id, user_id)` で、印は**観点ごと**に立つ。
「全数注釈が5文書」は次のどれとも読めるので、曖昧にしない。

1. 何らかの印がある `document_id` が5件
2. ある観点の印が5件
3. 種別ごとに5件

段2 の条件が「`D-01` の precision / recall が出ていること」なら実質 2 を要求する。
そのとき**段1 の注釈作業に `D-01` が含まれていなければ、印は溜まらない。**
文書・観点・種別の3軸を混ぜないこと。

### 共通観点

前の版は4本挙げたが、2本は落とすべきだった。

| 落とすもの | 理由 |
|---|---|
| 前の章と矛盾する記述 | `D-08` (章をまたぐ矛盾) と同じ。要件 §7 のモデル割当は `D-08` に Opus 5 を指定しており、共通観点に落とすと消える |
| 数値のない主張 | 既に `preset-ai-writing` の `no-ai-hype-expressions` と `ai-tech-writing-guideline` が取っている |

**後者の根拠に注意。** 前の版は要件 `L1-04` (自作ルールで定量化されていない形容を
検出) を根拠にしたが、**`L1-04` は未実装**である。`.textlintrc.json` には
プリセット2本しかなく、mdast を使う自作ルールも prh (`L1-03`) も無い。

実際に textlint を走らせた結果:

```
L5 no-ai-hype-expressions      「革命的な」という表現は過度に誇張的である可能性があります
L6 ai-tech-writing-guideline   【具体性】定量化されていない変化表現が検出されました
L6 no-ai-hype-expressions      「大幅に」という表現は誇張的である可能性があります
```

**「非常に高速に動作します」は検出されなかった。** 取れている語と取れていない語を
数え直し、取れていない分を L1 の辞書 (`L1-03` の prh) で足すのか、
共通観点に残すのかを決めること。

残す候補は「根拠なく断定している箇所はあるか」と
「読者が前提を知っている前提で書かれた箇所はあるか」。ただし後者は
**コメントに当てない** — コードコメントは定義上そのコードを読む人に向けて
書かれるので、ほぼ全件が該当する。

「散文の文書のみ」のような語を条件に使わない。文書種別で列挙すること。

### 種別固有の観点

| 種別 | 候補 |
|---|---|
| 設計書 | `D-01`〜`D-08`。要件で確定済み |
| README | 導入手順は動くか / 必要なものが書かれているか / できないことが書かれているか |
| CONTRIBUTING | 手順に判断の基準があるか / 迷ったときの決め方があるか |
| ADR | 状況・決定・代替案・結果が揃っているか / 代償が書かれているか |
| 要件定義 | 確定と未確定が区別されているか / 受け入れ条件があるか |
| 運用手順 | 失敗したときの戻し方があるか |
| コメント | コードの言い換えか / なぜが書かれているか / コードと食い違っていないか / 古くなっていないか |

**すべてに ID を振る** (00 の 4.1)。ID の無い観点は要件 `EV-02` の
「観点ごとに測る」を適用できず、`findings.aspect_id` にも入らない。

`D-07` (監視とロールバック) と `D-08` (章をまたぐ矛盾) は既存の意味のまま残す。
新設は `D-09` 以降。

### 種別の決め方と、誤ったときの回復

| 手段 | 使いどころ |
|---|---|
| パス名と見出しからの推測 | 初期値 |
| 利用者が画面で選ぶ | 上書き |
| 学習した分類器 | 将来。草案 `L4-05` |

**種別は `documents` ではなく `reviews` に持つ。** `documents` は本文 hash で
一意化されているため、そこに置くと上書きが過去の全レビューに遡って効き、
「このレビューではどの種別だと思って、どの観点を当てたのか」が再構成できなくなる。

種別を誤ると、当たらない観点が誤検知を出し、それが却下されて
**指摘の質と無関係な系統的バイアスが教師データに入る**。
`reviews.kind` に実績が残っていれば、後から「この種別のレビューは学習から外す」ができる。
残っていなければ回復不能なデータ汚染になる。

「共通観点は当たり続けるので全損はしない」という評価は、この点を見ていない。
失敗の様式は「検査が空振りする」ことではなく「誤った教師データが焼き込まれる」こと。

### 観点ごとのモデル

要件 §7 のモデル割当は `D-08` に Opus 5、他に Sonnet 5 を指定している。
`reviews.l3_model_id` は review に1つしか無い。
01 の `review_aspects` が `model_id` と `prompt_version` を持つので、そこに書く
(要件 `EV-05`, `L3-08`)。

### 共通観点を1回にまとめてよいか

要件 `L3-01` は「1プロンプトに複数観点を並べない」で**確定要件**。
まとめるなら要件の改訂が要る。「測ってから決める」は要件の扱いを決めていない。

判断には評価セットが要る。評価セットは 01 の全数注釈で作る。
**01 が動いてから判断すること。**

### 要件 §10 の finding スキーマに `aspect_id` を足すか

足さない場合、観点別 precision は API では集計できず、DB から直接測ることになる。
要件 `API-04` (層をまたいで同一スキーマ) と `API-05` (SARIF 変換) への影響を見ること。
